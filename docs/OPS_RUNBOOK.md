## 2. Deploying — and the trap that wastes an afternoon

```bash
ASSUME_YES=1 ./deploy_ionos.sh
```

**Static files always update. The Python API often does not.** IONOS shared hosting keeps the imported
Flask module resident behind the CGI wrapper and there is no way to restart it: no control panel button,
and the SSH session is a sandbox that can see neither the web worker nor any FastCGI socket. Touching
`cgi-bin/app.py`, touching `hvf_web/server.py` and clearing `__pycache__` were all tried and **none of
them work**. It clears when the worker recycles, on its own schedule.

So a deploy can report success, place every correct file on the host, and leave `/api/*` answering from a
module loaded hours earlier. This happened twice on 2026-08-22/23 and was noticed only because a new route
404'd — **a change that adds no route gives no signal at all**.

The deploy now compares `/api/build` against the fingerprint it shipped and warns on a mismatch. A
mismatch is a warning, not a failure: the static release IS live. Wait for the recycle and re-check before
concluding a `server.py` change did not work.

Two files under `data/` are deliberately overwritten by a deploy — `version_history.json` and
`build_id.json`, both generated by the build. The script aborts if the archive would touch any other
protected path.

## 3. When a scheduled job fails

The registry is `setup_cronjobs.py::JOBS` (cron-job.org → GitHub Actions `workflow_dispatch`).
**GitHub-native `schedule:` is banned** — never add one.

```bash
gh run list --workflow=<file>.yml -L 5
gh run view <id> --log | tail -50
gh workflow run <file>.yml --ref main          # re-run by hand
```

A green run is not proof the user-visible output is correct. Check where it actually lands.

## 4. Scanner snapshot / scan

A full scan is ~2 hours (yfinance rate limits, not code). `/api/status` reports `progress` while running.

```bash
gh workflow run trading-scanner-snapshot.yml --ref main
```

Supabase **Storage** has been returning 402 (a separate quota from the database). During the outage the
workflow seeds and publishes via IONOS instead. Publishing also re-warms the winners payloads (§5).

### What the outage actually costs you, learned the hard way on 2026-08-31

The outage itself was recorded here from the start. Three consequences were not, and they are the ones
that bit — the live site silently lost two weeks of data and 352 instruments.

1. **A green run does NOT mean Supabase was published.** The publish step carries
   `continue-on-error: true`, which rewrites its *conclusion* to `success`; only `outcome` holds the
   truth, and the gate fails only when *both* routes fail. Fourteen consecutive runs from 2026-08-16
   showed every step green while no row was written to `scanner_snapshot_versions`. The workflow now
   states which route carried each run, as a warning on the run summary. **To check the real state, ask
   the database, not the run:**

   ```bash
   ./.venv/Scripts/python.exe -c "from dotenv import load_dotenv; load_dotenv('.env');      import scanner_snapshot_store as s; print(s.current_metadata())"
   ```

   If `generated_utc` is older than today's scan, Supabase is behind and the IONOS copy is the only one.

2. **During the outage the newest snapshot exists in ONE place — the web host.** Supabase is not a
   restore point. The GitHub Actions artifact `scanner-snapshot` on the publish run is the other copy,
   retained 7 days; that is what the 30 August snapshot was recovered from.

3. **The web tier is remote-FIRST.** `scanner_snapshot_store.load_snapshot` used to overwrite the local
   file with whatever Supabase called current, with no recency check — so a worker restart replaced the
   good local snapshot with the two-week-old remote and served it. It now refuses a remote snapshot
   provably older than the local one, restores the local file (the pull has already overwritten it by
   then), drops the sidecar digest and logs at ERROR. Confirmed working in production on 2026-08-31.

**Symptom to recognise:** `/api/status` count drops (1,773 → 1,421) and the logged-out Performance tab
goes from ~2s to ~36s. The slowness is a *consequence*: precomputed winners payloads are keyed to the
live snapshot's `generated_utc`, so a snapshot that moves backwards invalidates every stored copy. The
cache is not broken — its key moved. Restore the snapshot and the speed returns on its own.

**To restore a snapshot to the host** (validate on the host before the move, and mind the permissions —
`umask 077` leaves it `-rw-------` where it must be `-rw-r--r--`):

```bash
gh run download <run-id> -n scanner-snapshot -D /tmp/restore
ssh "$IONOS_USER@$IONOS_HOST" "umask 077; cat > '$IONOS_DIR/hvf_web/.snapshot.tmp'" < /tmp/restore/snapshot.json
ssh "$IONOS_USER@$IONOS_HOST" "set -eu; cd '$IONOS_DIR/hvf_web';   python3 -c \"import json;d=json.load(open('.snapshot.tmp'));print(d['generated_utc'],d['count'])\";   mv -f .snapshot.tmp snapshot.json; rm -f snapshot.json.supabase.json; chmod 644 snapshot.json"
```

## 5. Best Settings is slow

Building one winners window costs ~33s and the page requests two. They are precomputed:

```bash
gh workflow run trading-winners-precompute.yml --ref main
```

A stored payload is used **only** when the snapshot generation time recorded beside it matches the live
one and it is under a day old — so any new snapshot correctly invalidates it. That is why the warm-up also
runs at the end of the snapshot publish. A missed precompute makes the page slow, never wrong.

Measured 2026-08-23: 34.9s / 16.9s cold → **1.5s / 2.1s** served from the store.

## 6. Backfills — the "built but nothing runs it" class

Both existed for weeks before anything invoked them. Symptoms are blank columns, not errors.

**New instruments have no 52-week range / no history.** The daily refresh audits only a 30-day lookback,
so a new ticker can never accumulate a year. Run the one-off deep backfill, in batches of ~115 to stay
inside the 30-minute job timeout:

```bash
gh workflow run trading-price-refresh.yml --ref main -f backfill_days=1100 -f tickers="AAA,BBB,..."
```

_2026-08-23: 345 tickers, 257,968 bars, ~9 minutes total, coverage 14.2% → 100%._

**New instruments have no sector.** Now scheduled weekly (06:00 Sunday), but runnable on demand:

```bash
gh workflow run trading-sector-backfill.yml --ref main
```

_2026-08-23: 438 resolved, coverage 28.4% → 99.5%. FX, gilts, commodities, indices and investment trusts
legitimately have no GICS sector._

**Neither takes effect on the site until a new snapshot is built** — sector is baked in at build time and
the 52-week map is cached against the snapshot timestamp.

## 7. Database size

Free-tier allowance is 500 MB. At 2026-08-23 it is **399 MB** after pruning.

```sql
select pg_size_pretty(pg_database_size(current_database()));
select relname, pg_size_pretty(pg_total_relation_size(relid)) from pg_stat_user_tables
order by pg_total_relation_size(relid) desc limit 5;
```

**A DELETE frees nothing measurable.** Postgres marks rows dead and reuses the space; `pg_database_size`
does not move. Reclaiming needs `VACUUM FULL`, which takes an ACCESS EXCLUSIVE lock.

- `price_history` (339 MB) is already at its 4.5-year retention — only 0.3% is prunable.
  `run_price_history_prune.py` is a dry run by default; its `--vacuum` step **must never be scheduled**,
  because the scanner, report and order bridge all read that table.
- `signal_log` was pruned 75% on 2026-08-23 (216,495 → 54,136 rows, 81 MB → 19 MB). It is static since
  the session monitors were disabled. When pruning it, **keep each ticker's most recent row**: every
  consumer reads `distinct on (ticker)`, and a plain date cut orphaned 12 of 61 tickers.

## 8. Email

`send_simple_email` / `send_trade_email` try Resend (HTTP), then fall back to Yahoo SMTP.

**GitHub runners block outbound SMTP**, so on a runner Resend must work — the fallback cannot rescue it.
Resend only sends FROM a **verified domain**. `config.EMAIL_FROM` is a yahoo.co.uk address, which Resend
rejects with a 403, so mail sends from `onboarding@resend.dev` — which Resend delivers **only to the
account-owner address**.

**To email anyone else you must verify a domain** at <https://resend.com/domains>, then set a
`RESEND_FROM` secret. No code change needed.

```bash
gh workflow run trading-email-test.yml --ref main
gh workflow run trading-scanner-report-email.yml --ref main -f only="you@example.com"
```

The Scanner Report is restricted to one address by default and is **not yet scheduled**.

## 9. Before believing anything

- Check the effect in live data, not the code path — see memory `built-but-never-invoked`.
- After a `server.py` change, check `/api/build` — see memory `ionos-resident-api-worker`.
- Never "optimise" `_winLedger`'s sort: `localeCompare` → `<` is 11% faster and moved the reported
  wallet by £1,037, because the replay compounds and the order IS the answer.
- Run the suite (`python -m pytest -q -m "not live_state"`, **466 tests** at 2026-08-25) before quoting
  any number. Use the project venv — on this machine the bare `python` is a system 3.14 with no pytest,
  and `python -m pytest ... | tail` will report **exit 0 while actually failing**, because the exit code
  comes from `tail`. Check `$?` on the pytest process itself.
