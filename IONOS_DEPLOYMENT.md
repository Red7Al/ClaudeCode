# IONOS deployment

Deploy with `./deploy_ionos.sh` (set `ASSUME_YES=1` to skip its confirmation prompt). It builds the
archive, refuses to ship anything that would clobber protected host paths, uploads, extracts, and then
verifies the live site — including, since 2026-08-23, that the API worker is actually running the build it
just sent. See "The resident API worker" below, which is the failure mode most likely to mislead you.

To build the archive alone, without deploying:

```powershell
python build_ionos_package.py
```

Before switching traffic:

1. Run `python migrate_runtime_state_to_supabase.py --apply` from a trusted machine and confirm every store
   reports `migrated` or `verified`. The command retains every local original.
2. Configure `SUPABASE_USER`, `SUPABASE_DB_PASSWORD`, `APP_SECRET_KEY`, `WEB_USERS_FERNET_KEY` and the
   dedicated server-only `SUPABASE_SCANNER_WEB_KEY` as IONOS
   environment secrets. `WEB_USERS_FERNET_KEY` must contain the existing key so current encrypted user/IG
   fields remain decryptable; never upload `data/.web_users.key` into the web root. The Scanner key must be
   a modern `sb_secret_...` Supabase key and must never appear in browser code, source control or a URL.
3. For IONOS Linux Web Hosting, extract the archive into the domain directory. The package's `.htaccess`
   serves static HTML directly and rewrites `/api/*` to `cgi-bin/app.py`; keep that adapter executable
   (`chmod 755 cgi-bin/app.py`). It uses `.venv_linux`, which can be created/refreshed with
   `python3 -m venv .venv_linux` followed by `.venv_linux/bin/python -m pip install -r requirements.txt`.
   `wsgi:application` remains available for VPS, Cloud Server or another persistent WSGI host.
4. Keep scheduled scans, order bridging and other background jobs in their existing scheduler. The heavy
   Scanner build is performed by `trading-scanner-snapshot.yml` and normally publishes to the private
   `scanner-artifacts` Supabase Storage bucket; configure its dedicated `SUPABASE_SCANNER_PUBLISH_KEY` as a
   GitHub Actions secret. During a Supabase Storage outage, the same workflow publishes the completed local
   candidate directly to IONOS as an atomic replacement of `hvf_web/snapshot.json`. Configure the GitHub
   Actions secrets `IONOS_HOST`, `IONOS_USER`, `IONOS_DIR` and multiline `IONOS_SSH_KEY` (plus optional
   `IONOS_PORT`) for that temporary route. The morning HVF report reuses its completed scan for the first
   publication and the evening Scanner job performs the second full refresh. WSGI may run
   several worker processes, so starting an order loop in every web worker would risk duplicate execution.
5. The archive contains the current `hvf_web/snapshot.json` only as a last-known-good boot cache. On startup
   and at a bounded cadence, the web tier verifies the current Supabase object and atomically refreshes that
   one local fallback. If Supabase is unavailable, the cron workflow's IONOS fallback updates that same file
   directly. The admin Refresh button dispatches the external worker; it does not scan on IONOS.

The package deliberately excludes local credentials and user data, development/test files, caches, logs,
working notes, source-control metadata, desktop launchers and historical zip archives.

## The resident API worker

**Static files always update. The Python API often does not.** IONOS shared hosting keeps the imported
Flask module resident behind the CGI wrapper, and there is no way to restart it: no control panel button,
and the SSH session is a sandbox that can see neither the web worker nor any FastCGI socket. Touching
`cgi-bin/app.py`, touching `hvf_web/server.py` and clearing `__pycache__` were all tried on 2026-08-23 and
none of them forced a reload; it clears when the worker recycles, on its own schedule.

So a deploy can report success, put every correct file on the host, and leave `/api/*` answering from a
module loaded hours earlier. This happened twice on 2026-08-22/23. It was noticed only because a NEW ROUTE
returned 404 — **a change that adds no route gives no signal at all**, which left two `server.py` fixes
shipped that day impossible to verify.

`/api/build` closes that hole. It reports the build the running **process** loaded, read once at import
(reading per request would report the file on disk, and the disk is not what is stale — a stale worker
would then report itself as current). `deploy_ionos.sh` compares it against the fingerprint it shipped and
says plainly when they differ. Check it any time:

```bash
curl -s https://www.squeezescanner.cloud/api/build
```

A mismatch is a warning, not a failure: the static release genuinely is live, and there is nothing to
restart. Wait for the recycle and re-check before concluding a `server.py` change did not work.

## Host paths

On an existing deployment, retain `.env`, `data/` and `.venv_linux/` when installing a new release, with
**two deliberate exceptions** under `data/`, both generated by the build and both meaningless unless
overwritten with the current release's copy:

- `data/version_history.json` — the release manifest the Version history tab falls back to, because the
  deployed package has no `.git` for its usual `git log`.
- `data/build_id.json` — the fingerprint `/api/build` reports.

`deploy_ionos.sh` enforces exactly that: it aborts if the archive would overwrite any other protected path,
which is how both of these were caught when first introduced. Everything else under `data/` — credentials,
the IG close audit trail, runtime caches — stays untouched. The
packaged `.htaccess` explicitly denies public access to those paths and to server-side source/configuration.
It also denies direct access to internal JSON, logs, archives, documents and generated guides; those remain
available only through the authenticated Flask API where applicable.
